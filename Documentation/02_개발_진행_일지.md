# 개발 진행 일지

## 이 문서의 용도

- **팀 보고서 겸 진행 공유**: 다른 팀원이 열어보고 **어느 시점까지 무엇이 구현·결정되었는지** 파악할 수 있게 한다.
- **결정·구현·이슈의 타임라인**: 날짜 단위로 쌓아, 나중에 “왜 이렇게 됐는지”를 추적한다.
- **코드와 독립**: Unity 빌드가 이 파일을 읽지 않는다. 사람·기획·AI 협업용 레퍼런스다.

---

## 일지 작성 규칙 (필수)

1. **날짜 헤더**: `## YYYY-MM-DD` 로 구간을 나눈다. 하루에 여러 번 기록할 경우 같은 날 아래에 `### 세션 이름` 또는 `### 오전` / `### 오후` 소제목을 둔다.
2. **팀이 바로 읽게**: 추상어만 쓰지 말고, **클래스명·씬명·Inspector 필드명·파일 경로**를 백틱으로 짚는다.
3. **무엇이 바뀌었는지**: “결정” / “구현” / “이슈·리스크·한계”를 구분해 적는다. 가능하면 **동작 변화**(플레이어 입장) 한 줄을 덧붙인다.
4. **프롬프트(요청 문구)**: 기획·에이전트·외주에게 전달한 **원문 요청**을 남기면 도움이 될 때만 인용한다. (길면 핵심 한 줄 + `…` 또는 요지만)
5. **문서·코드 불일치**: 코드에서 이름이 바뀐 경우(예: `FailOverlay` → `Blur`) 일지·개요 문서를 같이 고친다는 한 줄을 적는다.
6. **다음 액션**: 당일 못 끝낸 일·검증 필요 항목은 **알려진 한계** 또는 **다음 후보**에 명시한다.
7. **세분화(본 일지 기본 품질)**: 날짜 아래에는 반드시 아래를 채운다.
   - **진행도**: 영역별 완료 수준(표 + 필요 시 % 또는 `완료/진행/미착수`).
   - **변경 목록**: 수정·추가된 **파일 경로** 나열(스크립트·씬·문서 구분).
   - **동작 매핑**: “버튼/조건 → 코드 경로 → UI·오디오 결과” 한 줄씩.
   - **상수·기본값**: 코드 `const` / `[SerializeField]` 기본값과 **씬 YAML에 저장된 값이 다르면** 둘 다 적는다.
   - **검증**: 에디터에서 확인했는지 / 미확인이면 `미검증` 표기. **검증 체크리스트는 `05_*` 등 기술 문서에 두지 않는다** (`Project_Master_Context.md` §3).
8. **작업일**: `Project_Master_Context.md` §「작업일(날짜) 확인」 — **채팅(턴)마다** 오늘 날짜를 확인하고, 해당 `## YYYY-MM-DD` 아래에 기록한다.
